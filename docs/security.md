# Security and operations

## Trust and Kubernetes permissions

The backend is a reservation service and authenticated Kubernetes API gateway. Original cluster kubeconfigs remain AES-256-GCM encrypted in PostgreSQL and are decrypted only to establish upstream connections. Developers receive a stable gateway-only configuration containing the public gateway URL and CA, plus either an exec credential helper or a personal gateway token (PAT). No upstream token, private key or original Kubernetes endpoint is returned through normal connection APIs.

The gateway forwards the permissions already granted to the imported identity. It does not create or change Kubernetes RBAC, namespaces, Pod Security labels or network policies. An imported administrator identity remains powerful: a sufficiently privileged user may read Secrets, create privileged workloads or obtain other credentials through permitted operations. Hiding the original kubeconfig is not a hard boundary against that identity's allowed Kubernetes actions. Existing unmanaged credentials bypass reservations until separately restricted or revoked.

Only a single portable static context may be registered. Registration rejects HTTP endpoints, skipped TLS verification, executable plugins, external auth providers, file references, impersonation, username/password and proxy overrides. The CLI can minify and flatten approved source files locally. The browser admin import requires a selected static context with embedded data. Imported credentials are never executed as an external program. Registration, booking, selection and release do not contact or modify Kubernetes.

Administrators must register each physical cluster once. Endpoint aliases or duplicate kubeconfigs under different IDs are not automatically identified as the same cluster. Availability reflects reservations, not health, capacity, CNI enforcement or Kubernetes scheduling readiness. Reassignment can expose resources left by previous developers under the imported identity's permissions. Workload/data cleanup is manual; persistent-volume policies remain unchanged.

## Developer policy and primary selection

Identities use issuer plus subject, never email or a supplied name. Each developer has an effective maximum number of active bookings and one primary selection. The default maximum is 1; administrators can change the global default or set an individual override from 1 through 100. Shared bookings count in the same way as exclusive bookings. Limits apply across all profiles/devices for that identity. Reducing a limit does not evict holders; it blocks new bookings until the count is below the effective limit.

The first booking becomes primary. Additional bookings leave it unchanged. Selecting primary requires ownership of an active reservation. Stopping, expiring or administratively releasing the primary promotes the oldest remaining active booking, or clears it if none remain. Booking limits, placement, idempotency and selection updates run under PostgreSQL transaction locks, including across backend instances. No database transaction is held open during a Kubernetes HTTP call or stream.

The gateway endpoint is `/k8s`; it contains no session/developer/binding identifier. For every new Kubernetes request the backend validates its credential, resolves the authenticated developer's current primary, and verifies that reservation is active and unexpired. With no active primary, CLI and manual-only PAT access returns “no cluster is booked”; a valid PAT explicitly opted into automatic booking can instead reserve a matching unused cluster transactionally. Login, setup, credential creation/edits and refresh/heartbeats never allocate. The upstream destination is selected from registered server-side state, never a caller-supplied URL.

Requests are pinned to the reservation and selection version observed at start. Existing streams recheck the exact selected reservation and version. Changing primary closes a watch, exec or port-forward on the previous primary after the recheck interval/timeout; it does not migrate an open connection. Operations already dispatched to Kubernetes may finish and are not rolled back. Different terminals/devices using the same SSO identity deliberately share the same primary selection.

The default authorization recheck interval is 1s; `DEVCTL_GATEWAY_RECHECK_INTERVAL` accepts 100ms through 30s. Individual checks time out after 5s. Failed credential validation, revoked/expired PATs, release/expiry, primary changes and unavailable reservation state close streams. There is no claim of immediate interruption of a Kubernetes operation already accepted upstream. Kubernetes client discovery caches may retain previous-cluster information until refreshed even though routing follows the new primary.

## Cluster deregistration

Administrators can deregister a cluster through the CLI or browser with a nonblank audit reason. The same PostgreSQL reservation lock serializes deregistration with booking and expiry: live reservations reject removal instead of being silently evicted. There is no force-deregister operation; an administrator must explicitly release each booking through the existing audited release control first.

Deregistration sets the encrypted kubeconfig column to NULL and removes the cluster from placement, listing, maintenance and credential lookup. The archived public metadata row remains for foreign-key history, idempotent booking retries and audit identity. IDs remain reserved; display names may be reused. Historical session details remain readable. Repeated deregistration is idempotent and creates no additional deregistration audit event. This does not erase existing database backups/WAL or revoke credentials already used/copied outside the service. It makes no Kubernetes API call, removes no workloads/data and changes no PAT validity.

## Activity and reservation expiry

Administrators set a global inactivity grace period, default four hours and bounded from one minute through seven days. Booking duration and manual renewal are retired. Each active booking has a server-derived `expires_at` inactivity deadline. New bookings start a full window immediately. Migration gives existing active bookings a full window once; restarts do not reset it. Policy changes recalculate current deadlines from the recorded activity or migration baseline, so shortening the policy can expire an already-idle booking.

Qualifying activity extends only the current primary booking, never every cluster held by the identity. It includes authenticated Kubernetes requests, authorized open streams, explicit primary selection and an authenticated browser presence assertion. Automatic primary promotion does not refresh the promoted booking. Activity and expiry are serialized with PostgreSQL reservation locks; delayed or stale activity cannot revive an ended booking. Updates are throttled to limit database writes, so displayed timestamps are approximate within that interval.

The browser sends `/v1/activity` only after trusted key, pointer, wheel or touch input on a visible page, at most once every thirty seconds with one pending interaction. It clears pending presence on hiding/sign-out and pins assertions to the observed session and selection version. No repeating presence timer is maintained by an idle tab. The backend requires the authenticated owner, active current primary and exact version, accepts no client timestamps or requested extensions, and applies CSRF checks to cookie mutations. A client with valid SSO credentials can assert presence programmatically; this is coordination, not a proof of human presence.

GET polling, connection metadata, credential/token refresh and the CLI’s OAuth authorization heartbeat do not extend booking deadlines. A long-lived Kubernetes watch, port-forward or script does count while its gateway authorization remains valid, even when unattended. An unresponsive client or backend crash is not an immediate release signal: persisted inactivity deadlines and server-side expiry checks govern release.

Expiry ends the reservation and gateway access, then promotes the oldest remaining active booking if needed. It never deletes workloads, namespace data or volumes, never revokes a PAT and never changes the imported Kubernetes credentials. A workload can continue running after its owner becomes inactive and another developer books the cluster. Teams must handle workload/data cleanup separately.

## Authentication and credentials

The backend validates JWT access tokens using trusted OIDC discovery/JWKS, issuer, signature, API audience, expiry, an explicit access-token marker and approved group/role mappings. ID tokens are independently validated for login identity and are never API bearer credentials. The MVP requires signed JWT IdP access tokens; opaque provider tokens and SAML are unsupported.

The full CLI uses Authorization Code with PKCE S256, state and nonce, a loopback-only callback and a public native client without an embedded secret. Its kubeconfigs invoke the installed executable as a v1 ExecCredential helper. The helper refreshes existing credentials and can request interactive SSO only when kubectl explicitly permits interaction. Noninteractive missing login fails closed. Refresh tokens stay in the OS credential store; the explicit `DEVCTL_DEV_TOKEN_FILE=1` development fallback uses private 0600 files under a 0700 profile. Updates are atomic and use a cross-process lock to serialize refresh rotation.

An authenticated activity worker can renew a server-side OIDC authorization lease with a fresh validated access token. It is tied to the current primary reservation and selection version. A recent qualifying activity timestamp permits refresh; the authentication heartbeat and status calls do not keep themselves active. Updates are throttled, and the worker stops after two minutes without activity or when identity/selection/authentication changes. Activity is not proof of a human's presence: scripts and watches may run unattended. This OAuth heartbeat never extends the reservation inactivity deadline, bypasses IdP absolute limits or creates a booking. Reservation activity/expiry is enforced separately as described above.

PATs are opaque random 256-bit personal gateway credentials, stored only as SHA-256 digests and delivered once inside a native kubeconfig. New PATs grant `kubernetes:primary`: access to whichever active primary belongs to the same developer, not a fixed booking. Creation does not require a booking. Default lifetime is 8h with a 168h maximum; expiry is independent of the reservation inactivity deadline. The same file remains usable after an explicit later booking or primary switch, subject to the PAT's own validity.

A PAT cannot call the control/admin APIs, change an existing primary, edit its preferences, issue other credentials or acquire administrator rights. An explicitly enabled PAT has the limited automatic-booking capability described below. Issuing it as an app administrator still produces a developer gateway credential. Owners may revoke their own PATs; revoking another owner's PAT requires an administrator and an audit reason. Lists/audits contain metadata, not secrets/digests. A PAT does not rotate or slide its expiry: obtain a replacement through SSO after expiry/revocation. Browser download permissions are controlled by the browser; users must make the downloaded file private 0600.

A PAT snapshots the approved identity at issuance. Removing provider groups or disabling the provider account alone does not immediately revoke it. Offboarding must revoke the user's PATs and release reservations. Releasing bookings without revoking a PAT removes current access, but a still-valid PAT can access a later primary for that same identity; an opted-in PAT may create that reservation on its next gateway request. PAT revocation is the durable application-side credential control. No application operation revokes unrelated direct Kubernetes credentials.

## PAT automatic-booking preferences

Each PAT has mutable server-side `auto_booking.enabled` and equality-label `auto_booking.selector` metadata. Existing/new credentials default to disabled. Preference creation/edits never reserve capacity and never change the token digest, ID, expiry, downloaded file or current primary. Only an authenticated owner or approved administrator can edit; changes to another owner’s credential require an audit reason, and all changes are audited. Revoked, expired and retired-scope credentials cannot be edited or revived. Selectors accept at most32 valid Kubernetes label keys/values, including a present label with an empty value; a missing label does not match an empty selector value.

The gateway revalidates the PAT inside the reservation transaction. An existing primary always wins. When none exists and automatic booking is enabled, the same PostgreSQL advisory lock covers first-fit selection of an entirely unused, live, nonmaintenance cluster, normal booking/limit checks, primary assignment and activity. There is no automatic join of a shared environment. Concurrent first requests and backend instances cannot double-book, and a credential expiring during transaction work rolls the allocation back. Selector changes apply to future allocation only. No matching capacity fails clearly; it never chooses outside the rule or creates a cluster.

Logout and reservation stop/expiry preserve PATs. Therefore a still-valid opted-in PAT may allocate a replacement on its next Kubernetes request, including an automated retry after logout. Disable automatic booking or revoke the PAT when preventing subsequent automatic reservations is required. This does not bypass provider offboarding limitations: PAT identity remains the approved issuance snapshot, and administrators must revoke PATs during offboarding. These capabilities remain limited to registered upstream permissions and do not make devctl a cluster security boundary.

## Browser SSO and administration

Browser login uses a separate `devctl-web` client, Authorization Code with PKCE S256, one-time browser-bound state, and ID-token issuer/audience/signature/nonce validation. The API access token is validated independently and must identify the same issuer/subject. The callback is the exact configured public HTTPS origin plus `/auth/callback`; caller Host/query/forwarded headers do not choose it. An optional confidential web-client secret stays server-side.

OAuth credentials are AES-GCM encrypted in PostgreSQL under a separate associated-data namespace. Only browser cookie digests are stored. Login cookies use `Secure`, `HttpOnly`, `SameSite=Lax` and the `__Host-` prefix. JavaScript receives a session-specific anti-CSRF token and public identity information, never access/refresh tokens. The browser session survives backend restarts and has an absolute eight-hour default (`DEVCTL_WEB_SESSION_TTL`,1m through168h). A database compare-and-swap lease serializes rotating server-side refreshes without an open database transaction over the IdP HTTP call. A crash after provider rotation but before token persistence can require login again; failures fail closed.

Cookie-authenticated mutations require both the exact configured Origin and `X-CSRF-Token`. The UI uses a restrictive Content Security Policy and renders untrusted data as text. Administrator navigation is only a convenience: all limit changes, imports, maintenance, force releases, all-user token views, revocation and audit access are independently protected by backend role checks. Administrator force release uses the same reservation/primary updates as owner release and does not skip application authorization.

The UI assets, `/auth/login`, `/auth/callback`, `/healthz` and `/readyz` are public. `/web/session` and `/auth/logout` require a browser session. `/v1` accepts only a trusted API access token, including one injected from a validated browser session; it never accepts PATs. `/k8s` accepts either a trusted API access token or a valid user-scoped PAT. Browser cookies are never gateway bearer credentials.

The React/TypeScript UI uses the same cookie-authenticated API and backend OAuth flow. It stores no OAuth credentials or PATs in browser local/session storage. A requested one-time PAT kubeconfig and an administrator's import remain transient browser values; they are not persisted as application state. React renders user-controlled text through normal escaped JSX.

Slate's focused forms use native modal dialogs with an inert background, keyboard focus containment and focus restoration. Pending mutations disable dismissal and repeat submission. Sign-out and rejected application authentication cancel any pending confirmation before clearing the workspace, so an expired login cannot leave a stale action dialog over the sign-in page. These controls improve interaction safety; server-side authorization, ownership, CSRF and audit checks remain decisive.

`DEVCTL_FRONTEND_DEV_URL` explicitly enables a development-only proxy to a loopback Vite server. The backend listener and configured public HTTPS origin must also be loopback. The proxy accepts only named frontend paths, GET/HEAD and the HMR WebSocket; API/auth/gateway endpoints stay on their existing handlers. Cookies, bearer/CSRF/forwarded identity headers and Kubernetes bearer WebSocket subprotocols are stripped before the Vite request, and upstream cookies are discarded. HTTPS Vite targets retain normal certificate verification. Development CSP allows inline scripts/styles and WebSockets for React Fast Refresh; production keeps the restrictive CSP without those allowances. Keep this option unset in production, and never place secrets in frontend source or client-visible environment variables.

Logout releases all identity-owned reservations and clears the current local authentication/session, then attempts provider-supported OAuth refresh-token revocation. It does not revoke PATs or extend their expiry. The PAT remains valid after logout. A manual-only PAT needs a later explicit booking, while an opted-in PAT can book again on its next gateway request. Revoke PATs explicitly through the owner or administrator credential controls when durable credential revocation is required. It does not necessarily end every browser SSO session or invalidate a signed JWT before its expiry. Live primary checks still prevent use of an ended reservation. Closing a browser/terminal or deleting cookies does not immediately release bookings; after qualifying activity stops, the server releases them at the inactivity deadline. If logout cannot contact the backend, it reports failure; sign in again to verify/release retained reservations.

## Migration and secret handling

Migration preserves registered clusters, reservations, identities and audit records. The oldest active booking becomes primary. Legacy session-scoped PATs are revoked, never silently widened to developer-wide access. Historical records remain for audit. The `/k8s/sessions/...` and `/k8s/auto/...` connection flows are retired; run setup/download once to obtain the stable URL. Afterward, primary changes need no new kubeconfig.

Kubeconfigs use AES-256-GCM with fresh nonces and cluster ID as authenticated additional data. Keep the master key outside PostgreSQL, backed up separately in a secret manager or tightly permissioned environment. Key loss makes saved credentials unreadable; this version has no master-key rotation command. Access to both ciphertext and key exposes all credentials. Protect database accounts, backups and process inspection rights.

Do not log Authorization headers, cookies, OAuth callback queries, exec credential output, Kubernetes bodies, Secret contents, private keys or raw imported kubeconfigs. Strip caller Authorization/Cookie/impersonation/forwarded identity headers and bearer WebSocket subprotocols before forwarding. The upstream identity comes only from the encrypted server registry. Reject traversal, ambiguous paths, caller-supplied proxy destinations and credential-bearing redirects. Upstream audit logs identify the imported identity; devctl audit/selection records provide application actor correlation rather than Kubernetes impersonation.

CLI configs contain metadata only. Browser PAT YAML is a secret and may be copied. Shell integration writes only public connection settings and a config path; installation is explicit and normal commands do not edit global kubeconfig. Profile isolation separates local logins but not the backend limits/primary for a shared identity. Known app-owned legacy credential files are handled through bounded migration logic; arbitrary kubeconfigs, backups and other profiles are not swept.

## Transport and operational limits

Use verified HTTPS for the public gateway and independently verified TLS to Kubernetes. `DEVCTL_GATEWAY_CA_FILE` accepts certificates only; mixed/private-key bundles cannot be distributed as public trust. The demo permits HTTP only for its explicitly enabled loopback IdP. Use the exact public origin and approved browser callback, including 127.0.0.1 rather than switching to localhost during a demo login. Reverse proxies must preserve that origin and support streaming HTTP/1.1, WebSocket/SPDY upgrades, bounded control request sizes and appropriate stream timeouts.

Developers reach the gateway and IdP; the backend reaches the IdP and each Kubernetes API, possibly through a VPN. Run the backend outside the clusters it allocates. Back up PostgreSQL and the master key, monitor readiness, activity/expiry processing and database errors, and review residual workloads after released bookings. Define retention/access rules for team contact details, policy changes and audit events before production use.

Local tests use disposable PostgreSQL schemas, Keycloak and TLS Kubernetes API fixtures. They verify application state and API transport, not production admission/CNI/workload isolation, workload scheduling or every server streaming implementation. Corporate OIDC, desktop keyrings, production proxies/load, restore procedures and real-cluster behavior require deployment validation. Resource accounting, queueing, automatic cleanup, narrowed Kubernetes privileges, upstream credential rotation, SAML and opaque IdP access tokens remain deferred. See [verification](verification.md) for commands actually executed.
