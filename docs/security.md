# Security and operations

## Trust and Kubernetes permissions

The backend is an authenticated Kubernetes API gateway as well as a reservation service. Original kubeconfigs are encrypted in PostgreSQL and decrypted only on the server to establish upstream connections. The developer receives a gateway-only configuration, with the gateway address, public TLS trust information and a devctl credential-plugin invocation. It contains no upstream token or private key. The old raw-kubeconfig download endpoint no longer returns credentials.

For each request, the gateway verifies a trusted OIDC access token, approved application membership, ownership of the route's session, and an ACTIVE, unexpired reservation. It chooses the registered upstream from server-side state; the client cannot supply an arbitrary proxy destination. The upstream uses the imported static token or client certificate and verified TLS. The developer's Authorization token and identity/impersonation headers must not become upstream cluster credentials or trusted identity assertions.

The gateway does not create or alter Kubernetes RBAC. It uses the permissions already granted to the imported identity, including cluster-admin if that is what an administrator registers. It creates no namespaces, grants no new cluster roles, installs no policies and performs no automatic cleanup. Registration must be approved for the intended developers and use case. Existing unmanaged kubeconfigs and credentials distributed by earlier versions can bypass the gateway.

Keeping the original credentials off disk is not a hard boundary against a cluster administrator. A sufficiently privileged Kubernetes identity may read Secrets, create privileged workloads, or obtain other credentials through permitted API operations. The gateway forwards the imported identity's permissions; it does not filter the cluster API into a narrower application role. A future reduction of those permissions requires an explicit policy and rollout decision.

Administrators must register each physical cluster once: endpoint aliases or duplicate kubeconfigs under different IDs are not automatically recognized as one cluster. Neither registration nor booking proves cluster health, certificate expiry, CNI enforcement, resource capacity or reachability. Availability means reservation availability, not scheduling readiness. Reassigning a cluster may expose data left by previous developers under the imported identity's permissions. Users coordinate workload and storage cleanup manually; PV retention policies remain unchanged.

Only one portable context with embedded static credentials can be imported. The CLI minifies and flattens certificate file references locally. The server rejects insecure TLS, HTTP cluster endpoints, executable credential plugins, external auth providers, username/password, impersonation, proxy overrides and remaining file references. Static tokens or embedded certificate/key pairs are supported. The generated client-side devctl plugin is authored by devctl; the server does not execute an imported kubeconfig's plugin. Upstream credential rotation/renewal APIs remain deferred.

## Request and session lifecycle

1. OIDC access and refresh tokens authenticate the developer to devctl.
2. An active booking permits a gateway connection description and Kubernetes API requests for that session.
3. The local exec credential plugin refreshes existing devctl login if possible and returns an expiring, backend-intended OIDC access token to kubectl. Explicit session mode never opens a browser. The opt-in automatic kubeconfig permits first-use browser login only when kubectl provides an interactive terminal; automation without an existing usable login fails closed.
4. The gateway checks identity and the current booking before forwarding with server-held upstream credentials.

Stop, optional expiry, administrator release and logout prevent new requests through the released booking, even when a client retains a still-valid OIDC access token or a copy of its gateway-only YAML. Long-lived responses and upgraded connections are subject to periodic authorization/session checks and termination when those checks fail. The default recheck interval is `1s`; `DEVCTL_GATEWAY_RECHECK_INTERVAL` accepts `100ms` through `30s`. Checks have a `5s` timeout, so a stalled check closes a connection within roughly the interval plus that timeout. There is no separate fixed maximum stream duration: token expiry and lease end are enforced by rechecks. Requests already processed by Kubernetes are not rolled back; submitted Jobs and other workloads continue unless users stop them through a valid booking or administrators intervene.

Automatic bindings add an explicit reauthorization channel for existing streams. Every new request still needs a fully verified, unexpired access token. A separate authenticated heartbeat may renew a server authorization lease for that same issuer/subject, binding, and exact booking. Its expiry is capped by the new token's verified expiry and the booking expiry; request JSON cannot choose it. An established automatic stream can therefore continue after its initial token expires while fresh authentication renews that lease. Explicit session-ID streams retain their original-token checks. Neither route can continue after booking release or database/authorization failure.

Only actual gateway requests and authorized open streams count as activity; updates are throttled to once per 30 seconds. Heartbeat and activity-inspection calls do not keep themselves active. The detached renewal worker stops after two minutes without Kubernetes activity, when the identity/session changes, or when authentication fails. Activity is not proof of human presence: a watch or script can remain running unattended. No idle heartbeat policy releases a reservation or deletes workloads. The IdP's absolute session limit remains necessary. A stopped or expired automatic binding cannot allocate again; explicit setup with a fresh binding is required. Same-name users and reused client metadata do not transfer ownership.

Provider group/account changes follow the provider's JWT issuance and expiry semantics; rechecking a still-valid JWT does not query live group membership. Explicit session release remains the immediate application-side control. Provider refresh-token revocation is separate from booking release. An OIDC access token may remain cryptographically valid until its expiry, depending on provider behavior; the live session check still denies that released session. Existing raw Kubernetes credentials outside devctl remain valid until their own expiry or external revocation. No gateway operation rotates or revokes the upstream static credential. During current-profile initialization, the CLI detects embedded credentials in known app-owned legacy `s-UUID.yaml` and `active-kubeconfig` regular files and atomically replaces those records with inactive metadata. Inspection is bounded to 2 MiB and guarded against symlinks/inode replacement. Unknown filenames, other profiles, backups and original administrator kubeconfigs are not changed. Malformed/oversized legacy records fail closed and require manual action. This migration prevents normal reuse of those local app records; it does not revoke copies or recover secrets already disclosed. A backend URL change creates a different profile, so legacy profiles need separate attention.

The CLI uses an atomic, profile-wide active gateway configuration so all shells that load its integration observe subsequent selection changes. Selection does not migrate a running process's existing Kubernetes client. Logout writes an inactive configuration at the stable selected path. Stop does so only when the stopped session is selected. The environment setting and shell integration stay installed, so kubectl fails validation instead of falling back to the user's prior administrator configuration. Other profiles or copies of metadata may remain, but still require authentication and a valid booking.

Clearing browser cookies or closing a terminal does not end a reservation. If logout cannot contact the backend or refresh expired login, it clears local authentication, reports failure, and warns that bookings may remain active; log in again and stop them. Logout releases all reservations for that identity, not just the locally selected one. Other participants' bookings remain.

Kubernetes audit logs identify the imported kubeconfig identity, which can be shared by multiple developers. devctl's audit events identify the SSO actor and session associated with gateway activity, but do not change the upstream Kubernetes username into that SSO identity. Correlation depends on gateway records and timestamps; no Kubernetes impersonation is introduced.

## Secrets and transport

Kubeconfigs are encrypted using AES-256-GCM with fresh random nonces and cluster ID as authenticated additional data. PostgreSQL stores ciphertext. Metadata responses, generated kubeconfigs and audit details do not contain upstream credentials. Keep the master key outside the database, in a secret manager or tightly permissioned deployment environment, and back it up separately. Key loss makes registered configs unreadable. This version has no master-key rotation command. Anyone who obtains both database ciphertext and the key can recover all credentials. Use least-privilege database accounts and encrypted backups.

The public endpoints are `/healthz` and `/readyz`. Everything under `/v1`, `/k8s/sessions/`, and `/k8s/auto/` requires a trusted OIDC API access token and approved membership for new requests. Administrators alone can import configurations, set maintenance or release another user's booking with an audit reason. Developers may see team allocation/contact information, but may connect, stop, renew or share only their own booking; only its controlling holder may change sharing.

The gateway URL must use verified HTTPS, including loopback development; client-go skips exec credential authentication for an HTTP kubeconfig server. The identity provider may use explicitly enabled loopback HTTP in the demo only. Configure `DEVCTL_PUBLIC_URL` to the exact URL developers can reach (required for non-loopback deployment; local listeners may default to their loopback URL); the application does not trust an arbitrary request Host header to generate connection metadata. `DEVCTL_GATEWAY_CA_FILE` optionally supplies public CA trust data for that gateway. The backend-to-Kubernetes connection independently verifies the registered API's TLS certificate and optional configured server name. Upstream HTTP/1.1 is intentional so SPDY and WebSocket upgrades remain compatible with API servers that also offer HTTP/2. The CLI adds `DEVCTL_API_CA_FILE` to system roots for backend HTTPS and carries that nonsecret path into plugin/shell configuration. The demo generates a development CA and server certificate under `.demo/tls`; it never enables insecure TLS.

Automatic setup is deliberately offline and requires the REST API and gateway to share a public origin. It rejects a conflicting gateway URL returned by ensure. Its public CA bundle must contain certificates only; private-key or mixed bundles cannot be embedded in the generated YAML. Explicit session setup can continue to use separately configured API and gateway origins.

The backend refuses non-loopback HTTP listeners. Supply `DEVCTL_TLS_CERT`/`DEVCTL_TLS_KEY`, or bind to loopback behind a trusted TLS reverse proxy. That proxy must support long-lived responses, WebSocket/SPDY upgrades as required by client/server versions, and appropriate stream timeouts. It must also restrict request sizes/rates and strip untrusted forwarded identity headers. Avoid additional credential-bearing redirects and configure trusted destination endpoints.

Do not log Authorization headers, cookies, request/response bodies, upstream kubeconfigs, private keys, or credential-plugin output. Kubernetes API request bodies and responses can themselves contain Secrets. Do not enable broad HTTP body tracing. Restrict who can inspect the backend process, its environment and transport diagnostics. Do not put master keys, TLS private keys or database passwords in public configuration files.

The local generated YAML is intentionally readable configuration, not a secret container. The plugin's ExecCredential includes a sensitive devctl access token and is intended for kubectl's in-memory transport only. Tokens still reach developer processes; the security improvement is that the original cluster credentials are not distributed by normal devctl use.

Use the OS credential store for developer authentication. The demo's fallback is explicitly enabled with `DEVCTL_DEV_TOKEN_FILE=1`; token files and generated gateway configs are 0600 in a 0700 profile directory. Token updates use atomic rename and a cross-process lock. Shell integration writes nonsecret API/profile/identity-provider settings and a selected config path, never a token. Its installation is explicit and idempotent. Automated tests use temporary startup files rather than modifying the developer's real dotfiles. Linux is the tested host; other desktop keyrings and shell/browser behavior require deployment verification.

## Durability, networking and administration

The backend needs network access to registered Kubernetes endpoints and the identity provider, potentially through a VPN. Developer machines need access to the gateway and identity provider; the normal gateway path does not require direct Kubernetes API connectivity. Run the gateway outside the development clusters it allocates so those workloads do not host their own reservation control plane.

Migrations run under the PostgreSQL reservation lock. All reservation mutations and snapshots serialize on a transaction advisory lock across backend instances. No database transaction is held open during an upstream HTTP request or streaming connection. Backend restart preserves reservations and sharing. The expiry worker is idempotent across instances; API authorization also observes expiry without a persistent CLI.

Audit records cover identity checks, registration, booking, sharing, renewal, connection/gateway use, release, expiry, logout and maintenance. Neither imported kubeconfigs nor OIDC tokens belong in audit detail. Co-user names and email addresses are deliberately visible to approved team members. Define production retention and access policies for those records before rollout.

Maintenance blocks new allocations without evicting holders. Administrative release ends reservation access through the same gateway session checks as owner release; it does not clean a cluster. Back up PostgreSQL and the encryption key, monitor readiness and stream/expiry errors, and reconcile abandoned indefinite bookings manually.

Automated gateway tests use local disposable TLS API servers and local Keycloak/PostgreSQL. They do not prove real-cluster CNI, admission, workload scheduling, or every Kubernetes streaming combination. Corporate identity integration and production deployment have not been tested. See `verification.md` for checks actually executed. Opaque API tokens, SAML, cluster isolation, resource accounting, automatic cleanup, upstream/key rotation APIs and legacy credential revocation remain outside this version.
