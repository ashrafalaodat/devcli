# ADR 006: activity-based reservation retention

Status: accepted for the experimental MVP. Supersedes fixed booking TTL, manual renewal and the reservation-activity rules in ADR005. Gateway transport, primary selection, provider authentication and PAT validity remain separate controls.

## Context

Developers should retain a cluster while using it, then release it automatically after an administrator-defined inactivity period. A duration selected when booking and manual lease renewal do not express that policy. An identity may hold multiple clusters, but activity on one must not reserve every other cluster indefinitely.

## Decision

Remove the booking duration input, `start --ttl` and manual renew command/API. Keep one global durable inactivity grace period, initially four hours, configurable by an approved administrator from one minute through seven days with an audit reason. Update it atomically with the existing default booking limit when both fields are supplied; partial updates preserve other settings. Policy changes affect current and future reservations, including releasing an already-idle booking when the window is shortened.

Use server-side UTC activity timestamps. New bookings begin a full grace window immediately. Qualifying activity on the current primary extends only that booking. This includes authenticated gateway requests and authorized open connections, explicit primary selection, and authenticated browser presence assertions. Automatic promotion of an existing booking does not count. Reservation activity and expiry use the same PostgreSQL transaction lock as allocation, so stale heartbeats cannot revive ended reservations.

The browser records real input on a visible page and sends a version-pinned presence assertion at most once every thirty seconds. One pending input may be sent after throttling; the timer does not repeat without new input. Hiding the tab or signing out clears pending input. GET polling, an idle open tab, login, credential generation and OAuth refresh are not reservation activity. The backend rejects client-supplied timestamps/durations and checks owner, active primary and selection version.

Preserve `Session.expires_at` as the derived inactivity release deadline for existing wire consumers. It can advance with activity and is labelled Auto-release in the UI. Persist activity/deadlines in PostgreSQL and run expiry independently of clients. Database activity writes are throttled. Migration006 provides existing active reservations one full window using a separate baseline, without fabricating actual user activity or resetting the window on restart.

Keep the CLI/plugin OAuth refresh heartbeat as an independent authentication mechanism. Its authorization lease is bounded by verified token expiry; reservation validity is checked separately so advancing an inactivity deadline does not leave an active connection pinned to an old deadline. Neither OAuth refresh nor PAT lifetime grants a reservation. PATs keep their own fixed expiry and survive reservation expiry/logout until explicit revocation or expiry.

## Consequences

Using one cluster does not retain other held clusters. Selection remains identity-wide across terminals/devices, and the gateway pins each request to the observed primary version. Idle release updates reservation/primary/controller records and closes gateway access without changing Kubernetes or deleting workloads/data/volumes. Workloads may outlive the booking and require manual coordination before handover.

Activity is not proof of human presence. An unattended watch or script can hold its selected cluster, and an authenticated user can assert browser presence programmatically. This is acceptable for trusted internal coordination; per-user limits, administrator release and auditing remain available. Identity-provider absolute limits and PAT expiry still apply even during continued Kubernetes activity.

Tests must distinguish real input from idle tabs/polling, prove only the selected booking extends, serialize activity against expiry, retain deadlines across restart and preserve PATs/workloads on idle release. Local TLS Kubernetes fixtures prove gateway routing/transport; no corporate identity or real-cluster enforcement is implied.
