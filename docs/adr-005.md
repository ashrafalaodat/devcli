# ADR 005: developer primary cluster and one stable kubeconfig

Status: accepted for the experimental MVP. Supersedes the session-specific connection and automatic booking parts of ADRs002–004; their upstream-credential, transport and SSO trust decisions remain.

## Context

A developer should download or prepare a gateway configuration once, then book and switch environments through the backend. Session-specific URLs and fixed automatic bindings require new local configuration after booking changes and make it difficult to enforce a per-developer booking policy consistently across clients.

## Decision

Keep reservations as durable session records for ownership, TTL, sharing, history and administration. Add a developer profile keyed by the existing issuer-plus-subject ownership key. It stores an optional booking-limit override, a primary active reservation and a selection version. Administrators set a global default, initially one, and overrides from 1 to 100. Every active booking, including a shared booking, counts toward the effective limit across profiles and devices.

The first booking becomes primary. Additional bookings do not switch it. Selection accepts an owned active cluster/booking and changes the backend primary atomically. Ending the primary promotes the oldest remaining active booking or clears it if none remain. Reducing limits preserves existing reservations and blocks additional ones. PostgreSQL locking covers limit checks, idempotency, allocations and primary updates; no in-memory lock substitutes for database concurrency control.

All new kubeconfigs use the same public gateway URL, `/k8s`, without a session ID, binding ID or developer ID. The credential identifies the developer. The gateway resolves and checks that developer's current primary on every new request. With no active booking it returns the explicit error “no cluster is booked”; it does not allocate one. CLI/plugin login, setup, credential generation and token refresh never create bookings.

Browser PATs become developer-scoped `kubernetes:primary` credentials, issued without requiring a current booking. Their expiry is independent of booking expiry; they remain usable after an explicit later booking while the PAT itself is valid. They are individually revocable, default to eight hours, have a seven-day maximum and grant only Kubernetes gateway access. They cannot change primary, book environments, call control/admin APIs or issue other credentials. A refresh token in a plain kubeconfig is still unsupported: stock kubectl cannot execute the app's renewal flow without a helper. CLI/plugin credentials instead refresh through the OS credential store as before.

A request is pinned to the selected reservation and version when it starts. Streams periodically verify the credential, that exact active booking, and the unchanged primary version. Switching closes old connections instead of moving a running operation between clusters. A fresh authenticated heartbeat may extend the OIDC authorization lease for the same current selection during actual Kubernetes activity; it never extends bookings or creates one. PAT requests independently recheck the PAT and current selection.

Preserve existing bookings during migration and choose the oldest active booking as primary. Revoke existing session-scoped PATs rather than silently widening them. Remove the old automatic-binding runtime and retire `/k8s/sessions/...` and `/k8s/auto/...`; users perform one fresh setup/download. Historical audit data and migration files remain for traceability, not as alternate connection flows.

## Consequences

One downloaded PAT kubeconfig follows server-side selection until token expiry/revocation. Selection is identity-wide across terminals, browsers and machines, which the UI makes explicit. A copied credential has the same primary access and must be treated as a secret. SSO role removal alone does not immediately revoke a PAT: offboarding must revoke PATs and release reservations. Logout does both for the current identity.

Switching does not migrate workloads or undo completed Kubernetes operations. Client-side Kubernetes discovery caches may retain information from a previous cluster until refreshed; the gateway URL stays stable intentionally. Existing upstream permissions remain unchanged, including broad administrator permissions if imported. Resource accounting, workload isolation, queueing and automatic cleanup remain outside this reservation-only MVP.
