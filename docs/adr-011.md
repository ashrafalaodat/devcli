# ADR 011: audited registry-label editing with stale-write protection

Status: accepted. Extends the existing administrator cluster PATCH endpoint and Slate UI; no database migration, dependency or Kubernetes API operation is introduced.

## Decision

Allow administrators to replace the labels of a live registered cluster, including one with current holders or maintenance enabled. These are devctl placement labels, distinct from Kubernetes object labels. Use the existing `clusters.labels` JSONB column and reservation transaction lock so edits, placement and deregistration observe a consistent order.

The PATCH body accepts `labels` and a required `expected_labels` snapshot alongside an audit reason. Omission preserves labels; `{}` explicitly clears them; null, non-string values and duplicate JSON keys are rejected. New labels use the same Kubernetes syntax and32-entry limit as PAT equality selectors, including empty values. Validate new registration labels through the same rules. Expected snapshots are shape-checked without requiring new syntax rules, allowing repair of legacy metadata.

Compare the snapshot inside the transaction before changing any field. A stale snapshot returns409 with reload guidance and leaves both labels and any accompanying maintenance patch untouched. Compare logical map values rather than adding a revision column; equal current metadata is sufficient for this MVP. Existing maintenance-only requests remain compatible. Actual label changes audit the administrator, reason and before/after maps; no-op saves do not duplicate change events. Unexpected persistence errors return a generic503.

Use a focused Slate drawer with labelled key/value rows, add/remove controls, linked validation errors, a required reason and busy guards. Keep its original snapshot and draft stable through background refreshes. A conflict retains the draft and disables saving until the administrator explicitly reloads current labels. Reload replaces the draft, announces the result and restores useful keyboard focus. Recoverable failures preserve input for retry.

## Consequences

Future manual or automatic placement uses the edited registry. Existing reservations, identity-wide primary selections, credentials and PAT preferences remain unchanged. An existing primary still takes precedence over a PAT selector, even when its labels no longer match. Clearing or changing a required label can remove a cluster from subsequent matching; the editor explains that effect.

This endpoint grants no new developer or Kubernetes permission. Only approved administrators may change metadata, browser mutations retain Origin/CSRF checks, and every stored credential remains server-side. Durable-state/API tests cover concurrent edits and allocation/deregistration ordering; browser tests cover validation, failure recovery, conflict reload and keyboard/mobile controls. Real local Keycloak integration separately verifies the browser-authenticated API and future PAT placement through TLS protocol fixtures.
