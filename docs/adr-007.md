# ADR 007: cluster deregistration with preserved history

Status: accepted for the reservation-only MVP.

## Context

Administrators need to retire registry entries through both the CLI and browser, remove stored credentials and prevent future bookings. Historical sessions reference cluster IDs, and creation idempotency keys must keep returning the original booking rather than allocating a different cluster.

## Decision

Add administrator-only `DELETE /v1/admin/clusters/{id}` with a nonblank audit reason, `devctl admin deregister CLUSTER_ID --reason ...`, and a confirmed browser action under cluster placement controls. Use the existing PostgreSQL advisory transaction lock shared by booking, release and expiry. Process legitimate elapsed reservations, then reject removal if any active booking remains. Require explicit audited release of those bookings first; add no force-deregister flag.

Migration007 adds `deregistered_at` and permits a NULL kubeconfig only on an archived, nonshared maintenance record without a controller. Deregistration NULLs the encrypted credential and retains only public cluster metadata, sessions, idempotency keys and audit history. Live registry snapshots, placement, selection, maintenance and credential lookup exclude archived records. Historical booking details can retrieve safe archived metadata.

Retired IDs cannot be reused. A partial unique index allows display-name reuse among new IDs while preserving the original historical row. Repeating removal of an already archived ID succeeds without another audit event; an unknown ID returns404. A new registration requires a new ID and fresh trusted credential import.

## Consequences

Deregistration changes application state without contacting Kubernetes, removing workloads/storage, revoking upstream credentials or changing PAT validity. Removing a current database value is not a secure-erasure guarantee for backups/WAL; existing backup retention and credential rotation policies remain necessary. Browser confirmation describes the concrete removal and requires a reason, while server validation remains authoritative if another booking races the UI.

Tests must prove administrator authorization, CSRF, active/shared-booking conflicts, book-versus-deregister concurrency, removal of ciphertext, preservation of history/PATs/other registry entries, idempotence, name reuse with ID reservation, and restart stability. Integration tests use isolated local PostgreSQL schemas and TLS fixtures; no registered remote cluster is retired for testing.
