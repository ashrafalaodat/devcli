# ADR 009: React and TypeScript frontend with Vite development

Status: accepted. Replaces the imperative browser implementation while retaining the reservation, primary-selection, PAT, inactivity and authentication decisions in ADRs 005–008.

## Context

The browser client now includes developer and administrator workflows, editable PAT preferences and interaction-based reservation activity. Keeping these features in one JavaScript file with manual DOM replacement makes state transitions and further frontend work difficult to maintain.

## Decision

Keep the Go backend and existing HTTP API contracts. Move the editable frontend source into `frontend/`, using React 19.3.1, React DOM 19.3.1, TypeScript 7.0.2 and Vite 8.3.8, with exact dependency versions and the npm lockfile committed. Use typed functional pages, shared UI components, a CSRF-aware API client and a presence hook. Preserve the current layout, public workflow and developer/administrator controls; introduce no new identity flow or database migration.

Use React state for rendering and controlled forms. Retain a booking's idempotency key across retries until its input changes. Serialize refresh reads so an older in-flight snapshot cannot replace the result of a later mutation. Trusted visible input can send version-pinned presence, while idle tabs and passive reads do not renew reservations. OAuth credentials remain on the backend; one-time PAT downloads and administrator kubeconfig imports are transient request/download data rather than browser storage or application state.

Vite produces three stable files: `internal/webui/assets/index.html`, `app.js` and `app.css`. Disable production source maps and code splitting. Commit the generated assets so direct Go-only builds and tests remain usable; Make and the container build regenerate them from the TypeScript source. The runtime serves the embedded files through the existing named asset allowlist with strict CSP, no directory listing and no Node.js process. Node is a frontend build/development dependency only.

## Development origin

Run Vite on loopback port 5173 and explicitly enable the Go asset proxy with `DEVCTL_FRONTEND_DEV_URL`. Continue opening the normal verified HTTPS backend origin, default `https://127.0.0.1:9090`, rather than moving authentication to another browser origin. SSO redirects, secure cookies, API requests and CSRF checks retain their existing origin; no identity-provider redirect change or insecure TLS setting is required.

The proxy accepts a validated loopback origin and only the frontend module, dependency-cache, React refresh and HMR paths needed by Vite, including the exact `node_modules/vite/dist/client/env.mjs` path. It rejects private, traversal and unrelated source paths. Authentication, cookies, CSRF and identity-forwarding headers are stripped before requests reach Vite, and frontend responses cannot set authentication cookies. WebSocket upgrades are limited to the HMR endpoint. Only explicit development mode relaxes CSP for Vite's refresh preamble and style injection; production keeps its existing strict policy.

## Consequences and validation

Frontend contributors get TypeScript checking and React hot reload while deployment remains one Go service. Generated assets must accompany source changes, and rebuilding adds a pinned npm dependency step. Existing client and backend contracts remain compatible, with no new reservation permissions or Kubernetes operations.

Validation includes strict TypeScript and API/label unit tests, the existing browser contracts, expanded registration/maintenance/release workflows, held-response stale-snapshot ordering, production-CSP checks and a smoke test of verified TLS and HMR. Browser fixtures reject external HTTP destinations and make no Kubernetes calls. Real Keycloak and gateway integration tests remain separate; no corporate identity system or registered remote cluster is changed by this migration.
