# ADR 002: server-side Kubernetes gateway and public client configuration

Historical record: [ADR008](adr-008.md) defines the current two-client model and editable PAT fallback. The standalone kubectl subcommand client described in older decisions has been removed.

Current connection and selection behavior is defined by [ADR005](adr-005.md). Session-specific URLs, fixed automatic bindings and implicit booking described below are historical and have been replaced by one developer gateway and an explicit primary selection.

Accepted following the request to keep original kubeconfigs off developer machines. This supersedes ADR 001's direct kubeconfig-delivery design; its reservation and identity rules remain unchanged.

The backend stores encrypted, portable static kubeconfigs and uses them to forward Kubernetes API requests. Developers retain local kubectl and other compatible Kubernetes clients. The backend does not execute their shell commands. A command such as `kubectl apply -f deployment.yaml` reads the local manifest and sends API requests to the gateway; only those requests are forwarded to the registered API endpoint.

The developer-facing kubeconfig contains the public gateway URL for one session, public gateway CA data when needed, and a standard `client.authentication.k8s.io/v1` exec invocation of the devctl binary. It contains no upstream endpoint credential, client private key or cluster token. `GET /v1/sessions/{id}/connection` returns this public connection metadata only for the authenticated active owner. The former raw-kubeconfig endpoint returns no original credentials.

The devctl credential plugin uses an existing login and refresh token where available; it does not open a browser from kubectl. It returns a backend-intended OIDC access token and its real expiry through ExecCredential stdout. The API server does not need to trust that OIDC provider because only the gateway consumes the developer's token. Backend signature, issuer, audience, expiry, access-token marker and group checks remain enabled. The gateway uses independently trusted server-held Kubernetes credentials upstream.

Each gateway request is bound to a recorded session, verifies its owner, active state and optional expiry, and selects its destination from the server-side registry. The caller cannot turn it into an arbitrary forward proxy. The incoming developer credential and impersonation headers are not forwarded as cluster identity. TLS is verified on both the developer-to-gateway and gateway-to-cluster hops. Gateway URLs require HTTPS even on loopback, because client-go skips exec credential authentication for HTTP kubeconfig servers. Optional public CA trust is carried in generated YAML, while `DEVCTL_API_CA_FILE` supplies CLI control-plane trust. The demo generates a development CA rather than bypassing validation. Public connection URLs come from configured deployment values rather than client-controlled Host headers.

Kubernetes uses both ordinary HTTP and streaming/upgraded transports. The gateway must forward query strings, API discovery and payloads while supporting streaming responses and bidirectional upgrades used by exec/attach/port-forward. Upstream transport intentionally selects HTTP/1.1 so SPDY upgrades are not accidentally sent over a negotiated HTTP/2 connection; normal WebSocket upgrades also use HTTP/1.1. It performs ongoing authorization checks for long-lived requests and terminates those connections when the reservation or permissions are no longer valid, subject to `DEVCTL_GATEWAY_RECHECK_INTERVAL` (default 1s, configurable from 100ms to 30s) and the 5s timeout for a stalled authorization check. There is no separate fixed maximum stream duration. Already processed Kubernetes requests are not rolled back. Local transport tests are necessary, and do not replace validation against an approved disposable real cluster before a production rollout.

`start` selects its resulting booking. `select SESSION_ID` changes a stable active kubeconfig file for the current login profile. Shell integration sets KUBECONFIG to this path in Bash, Zsh or Fish, so all shells using that profile see later selection updates. Installation is explicit, additive and idempotent; the developer's global kubeconfig is not overwritten. Logout writes an inactive config at that stable path; stop does so only for the selected session. KUBECONFIG remains set so access fails closed rather than automatically reverting to a prior administrator context. Separate profiles still support separate developer identities or independent selections when explicitly desired.

This moves reservation enforcement to the gateway without changing cluster RBAC. Imported identities retain their existing full-cluster permissions. The gateway does not provision environments, install policies, create clusters, rotate upstream credentials or delete workloads/storage. Existing original kubeconfigs bypass it and require separate revocation/rollout controls. A privileged cluster identity can still access or create other credentials through permitted Kubernetes operations, so keeping the original kubeconfig server-side is not a hard security boundary against a cluster administrator.

The single-backend application retains PostgreSQL-backed transactions for bookings and sharing. Transactions complete before network forwarding. Streams revalidate live state without holding a reservation transaction open. The design adds neither Redis nor a separate container command-execution service. It requires developers to reach the gateway and the backend to reach registered APIs; gateway availability and bandwidth now affect all client operations.
