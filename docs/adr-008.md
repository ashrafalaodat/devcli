# ADR 008: editable PAT fallback and two supported clients

Status: accepted. Supersedes ADR005’s manual-only PAT allocation rule and ADR004’s standalone kubectl subcommand client. Existing primary, identity, TLS, inactivity, deregistration and credential-secrecy decisions remain.

## Decision

Support the full `devctl` CLI and browser UI. Remove the standalone `kubectl-devctl` command, package/installer/build target, executable entry point, product cards and dedicated tests. Retain the full CLI’s standard Kubernetes exec credential helper and OAuth renewal, which are necessary for its normal kubeconfig. Browser/PAT kubeconfigs use stock kubectl without a helper.

Persist optional `auto_booking` metadata alongside each PAT digest: an enabled boolean and an equality-label selector. Migration008 defaults existing credentials to disabled. New credentials are also disabled unless explicitly opted in. UI and full CLI can create or edit preferences through SSO-authenticated API calls. Owners may edit their own records; administrator changes for another owner require an audit reason. Reject expired/revoked/retired credentials. Policy changes preserve the token/ID/digest/expiry and never rewrite a downloaded file or alter a current booking.

A PAT cannot authenticate the control API or change its own policy. On a Kubernetes gateway request, validate it and resolve its owner’s current primary under the existing PostgreSQL reservation lock. Any existing primary wins regardless of selector. If absent and enabled, choose the first entirely unused live, nonmaintenance cluster matching every equality label. Use the standard booking/limit/inactivity path and assign primary in the same transaction. Automatic fallback does not join a holder’s shared reservation. Empty selector means any unused cluster. No match returns a useful native kubectl error without selecting outside the rule. No queue, cluster creation or migration is introduced.

Selector validation follows Kubernetes label rules with at most32 entries. An empty value matches only a present label with that value. Multiple first requests/backend instances create one booking. Recheck token expiry before commit; credential failure rolls back a new allocation. Editing, login, setup, refresh and passive reads do not allocate.

## Consequences

The same PAT/kubeconfig follows later preference edits and primary changes. A new selector affects only future allocation, avoiding disruption to running work. A valid opted-in PAT can reserve again after stop, inactivity expiry or logout on its next request; disable automatic booking or revoke it to prevent that behavior. PAT expiry remains fixed and logout never silently revokes it. Already open streams are still pinned to the booking/version they started with.

The selector is server-side state rather than arbitrary kubeconfig metadata, so standard Kubernetes clients need no custom installation. It is a placement preference, not an authorization boundary: the developer’s existing primary can be outside this selector. Registered credentials and their broad Kubernetes permissions remain unchanged. No corporate identity system or real cluster is modified by local verification.
