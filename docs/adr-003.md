# ADR 003: automatic kubectl access and activity-driven authentication renewal

Historical record: [ADR008](adr-008.md) defines the current two-client model and editable PAT fallback. The standalone kubectl subcommand client described in older decisions has been removed.

Current connection and selection behavior is defined by [ADR005](adr-005.md). Session-specific URLs, fixed automatic bindings and implicit booking described below are historical and have been replaced by one developer gateway and an explicit primary selection.

The normal developer workflow should require only kubectl after one installation. Keep the backend gateway and reservation rules from ADR 002. Add an opt-in automatic kubeconfig instead of a kubectl subcommand plugin or a replacement kubectl executable.

## Setup and identity

`devctl setup` creates a private local binding ID and a gateway-only kubeconfig. Setup does not log in, contact Kubernetes, or reserve capacity. The kubeconfig invokes the installed devctl binary as an exec credential helper with `interactiveMode: IfAvailable`. On first interactive use, the helper runs the existing Authorization Code flow with S256 PKCE, state, nonce, and a loopback callback. On a headless SSH host, it can print the browser URL using `DEVCTL_NO_BROWSER=1`. A noninteractive process without a usable login fails with instructions rather than launching a browser.

The helper retains refresh tokens in the OS credential store, with the existing explicit private-file development fallback. Only the backend-audience access token is returned to kubectl. Concurrent refreshes use the existing profile lock and save replacement refresh tokens atomically. Manual session kubeconfigs retain their noninteractive credential behavior.

## Reservation binding

The new stable URL is `/k8s/auto/{binding}/...`. An authenticated ensure request transactionally binds issuer plus subject and the binding ID to a compatible owned active session, or allocates one using the existing deterministic scheduler. The durable binding records the booking parameters and exact session identity. Concurrent discovery, retries, and multiple terminals reuse that reservation.

Gateway requests only resolve existing bindings. They never allocate capacity. Stop, expiry, logout, and administrator release invalidate access without moving the client to another cluster. A later ensure request for an ended binding fails. `setup --new-booking` is the explicit reactivation step; changing booking parameters also requires that step. Existing manual commands remain available for session management and administration.

## Activity and long-running connections

Actual authenticated Kubernetes requests and authorized open streams update the session's `last_activity_at`, with writes throttled to once per 30 seconds. Control-plane activity queries and heartbeat requests do not count as Kubernetes activity. This is client activity, not proof of human presence. No missing heartbeat deletes workloads or automatically releases a reservation.

The helper starts one detached heartbeat worker per binding and session. It uses the same credential store, never opens a browser, and polls after 15 seconds and then every 15 seconds. It exits when the binding ends, identity/session changes, authentication fails, or Kubernetes activity is older than two minutes. The worker refreshes access tokens on demand and sends an authenticated heartbeat. The server accepts renewal only while recent Kubernetes activity exists, and never trusts a client-supplied expiry.

New gateway requests always need a valid OIDC access token. For automatic bindings, an existing stream may continue after its original token expires only while a server-side authorization lease has been renewed with another valid token for the same identity and exact reservation. The lease is capped by the verified token's real expiry and the booking expiry. Stop, authorization-lease expiry, and database failures still close the stream. This separate reauthorization channel avoids trying to replace the HTTP Authorization header on an established connection. Older session-ID routes retain the stricter original-token expiry behavior.

## Lifetime policy and distribution

New demo realms request ten-minute access tokens, a one-day SSO idle timeout, a seven-day absolute SSO session maximum, and refresh-token rotation. Existing persistent realms retain their configured policy; operators must update those settings through Keycloak administration. An organisation's provider owns its idle and maximum session policy. The helper does not extend those limits or fabricate token expiry.

`make client-package` creates a native client archive with the helper and a one-time installer. The installer configures the automatic kubeconfig using approved gateway and issuer URLs. Optional shell integration is explicit. Packaging excludes server configuration, encryption keys, stored tokens, and upstream kubeconfigs. This remains a local Kubernetes client using a central API gateway; no remote shell execution service or additional infrastructure is introduced.
