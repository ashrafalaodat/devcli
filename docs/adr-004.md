# ADR 004: three clients and browser-only personal credentials

Historical record: [ADR008](adr-008.md) defines the current two-client model and editable PAT fallback. The standalone kubectl subcommand client described in older decisions has been removed.

Current connection and selection behavior is defined by [ADR005](adr-005.md). Session-specific URLs, fixed automatic bindings and implicit booking described below are historical and have been replaced by one developer gateway and an explicit primary selection.

Status: accepted for the experimental MVP.

## Context

Developers need different amounts of local tooling. The existing full CLI supports reservation management and administrator operations. Some developers want only a small kubectl extension; others want stock kubectl without installing a helper. All clients must keep original cluster credentials on the gateway and preserve the same durable ownership and reservation checks.

Stock kubectl can send a bearer token from its kubeconfig, but it cannot perform our browser SSO flow or rotate that token without a local credential helper. A refresh token inside a plain kubeconfig would therefore add a sensitive secret without implementing renewal.

## Decision

Keep the full `devctl` CLI. Add `kubectl-devctl`, discovered as `kubectl devctl`, with login, setup, status and logout only. It reuses the CLI's public OIDC client, PKCE S256, state/nonce validation, OS credential store, refresh locking, refresh-token rotation, automatic booking and activity renewal. Generated exec configurations invoke the executable that authored them, so the plugin needs no separate devctl installation. Reduced command visibility does not reduce or expand server-side permissions.

Add an embedded browser UI and a backend-for-frontend session. A separate web OIDC client uses code flow with PKCE, one-time browser-bound state and nonce. OAuth credentials stay encrypted in PostgreSQL; the browser receives an opaque Secure/HttpOnly/SameSite cookie. Cookie-authorized mutations require an exact Origin and anti-CSRF token. Browser sessions have an eight-hour default absolute lifetime. A database-backed refresh lease serializes rotating refresh grants across backend instances without keeping a transaction open over provider HTTP calls.

After browser SSO, a developer books a cluster and issues a personal access token for that exact owned active booking. The one-time download is a native kubeconfig containing the gateway URL, public CA and opaque PAT. It contains no exec helper, OIDC refresh token, original cluster endpoint, original cluster token or client key. The PAT is random, stored as a SHA-256 digest, individually revocable, valid for eight hours by default and at most seven days, capped by reservation expiry. It grants only Kubernetes gateway access to its one session. It cannot call the control API, administer the backend, create reservations, or issue/renew credentials.

PAT expiry is fixed, not sliding. Native kubectl users obtain a replacement through browser SSO. The CLI/plugin paths provide seamless access-token refresh instead. Expired or stopped automatic bindings never silently book another cluster. PATs also cannot rebook after a session ends.

Administrators use SSO-protected UI controls for registration, maintenance, audited release, credential revocation and audit inspection. Owners manage their own bookings and personal credentials. Browser logout matches CLI logout: release all bookings for that identity, revoke its PATs, clear the local session and attempt provider refresh-token revocation. Other developers' bookings and all cluster workloads remain.

## Consequences and limits

No-install means no extra executable beyond kubectl; configuration and a sensitive gateway credential still reside on the developer's machine. Browsers cannot guarantee private download permissions, so users must protect downloaded files. A PAT is a gateway credential, not the upstream kubeconfig. Its approved identity is captured at issuance; IdP membership removal requires explicit application-side PAT revocation or booking release for immediate offboarding.

Gateway requests and streams recheck reservation state and PAT expiry/revocation. Already accepted Kubernetes operations are not rolled back. Broad permissions in an administrator-imported upstream kubeconfig remain broad; no cluster RBAC or workload isolation is added by these client options.

Existing persistent Keycloak realms need the new web client imported without recreating users. Fresh realms include it. Corporate provider setup, browser/private-CA trust, desktop keyrings and production deployment still require organisation-specific validation. The verification record distinguishes executed tests from untested integrations.
