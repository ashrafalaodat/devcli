# ADR 001: kubeconfig reservation MVP

Accepted following the revised product scope. The direct kubeconfig-delivery sections are superseded by [ADR 002](adr-002.md); the reservation, sharing, identity, and transaction decisions remain in force.

The backend coordinates existing cluster access. It stores AES-256-GCM encrypted, portable static kubeconfigs and durable bookings in PostgreSQL. It never provisions namespaces or changes Kubernetes authorization. client-go's kubeconfig parser is used locally; there is no Kubernetes API client in the runtime.

A single Go backend contains the REST API, transactional first-fit booking logic, and an optional-expiry worker. PostgreSQL transaction advisory locking serializes all reservation changes across server instances. Transactions include only database work, never discovery, token exchange, remote API calls, or process execution. This is deliberately simple and limits throughput, which is acceptable for internal cluster booking. Read snapshots also use the lock to reflect coherent sharing/expiry state.

Empty clusters are preferred, sorted by stable cluster ID. Occupied clusters may be joined only after their controller explicitly enables sharing and while below the participant cap. The default cap is two. Conflicts are rejected instead of queued. One active booking per identity per cluster is enforced by a unique partial index. Idempotency keys are durable, bound to identity and request hash, and never replay as a new reservation.

The first booking controls sharing. On controller departure, the oldest remaining holder is promoted and sharing resets to private. Turning sharing off never evicts current participants. A cluster becomes available immediately after the final booking ends; this does not mean its workloads are clean or previous credentials are invalid. Coordination of remaining workloads is manual.

There is no default TTL: bookings last until stop or logout. An explicit optional TTL supports automatic release when desired. The expiry worker runs every five seconds; API transactions also enforce expiry, including after restart. Sessions are ACTIVE, RELEASED or EXPIRED. Only ACTIVE sessions occupy a booking slot. There are no provisioning/cleanup states because no Kubernetes operation occurs.

OIDC identifies developers by issuer plus subject and verifies API access tokens against the configured audience and explicit access-token marker. CLI login uses PKCE, state, nonce, and a fixed, approved loopback redirect. Standard refresh tokens suffice for the demo; offline_access is optional and requires additional provider permissions. No client secret is embedded.

The original namespace-isolation, workload-cleanup, temporary ServiceAccount, resource-budget, exclusive-draining, and kind requirements are superseded for this version. Future security enforcement requires a separate design and migration; encrypted storage does not make copied credentials revocable.
